## 0. まず先に報告すること（実装前の確認事項）

指示書に「既存データを壊す可能性がある変更は、実装前に報告してください」とあるので、先にこれを書きます。
**3件あります。**

### ① 指示書の構成と、いまのアプリの約束が食い違っています

いまの `seiza/README.md` にはこう書いてあります。

> ブラウザだけで動きます。記録はこの端末の中だけに保存され、どこにも送信されません。

`assets/store.js` の1行目にも同じことが書いてあります。そして実測でも、**アプリ側のコードに外部通信は1件もありません**（第1章の調査結果）。

指示書のバックエンド構成をそのまま作ると、この約束は成り立たなくなります。
壊れるのはコードではなく**書いてある約束**なので、勝手に消さずに選択肢を出します。

| 案 | 中身 | 約束の扱い |
|---|---|---|
| **A** | いまのまま。外部接続なし。診断JSONの手動やりとりだけ | そのまま守られる |
| **B（推奨）** | 外部接続は**任意の追加機能**。使わない人は今までどおり。使う人だけ、送る項目を画面に出したうえで繋ぐ | 「既定では送信しない。繋いだときだけ、これを送る」に書き換え |
| **C** | 指示書どおり常時バックエンド | 全面的に書き換え。無料では済まなくなる |

**推奨は B** です。理由は第3章。

### ② 「進捗率を下げない」要件は、いまの計算式では守れません

いまの習得率は `assets/calc.js` でこう出しています。

```
習得率 ＝ 全部の星の合計点 ÷（星の数 × 4）
```

星が増えると**分母が増える**ので、何もしていなくても率は下がります。
自動収集で星が増える以上、ここは必ずぶつかります。実装前に決めたいので、案を出します。

| 案 | 中身 | 欠点 |
|---|---|---|
| **A（推奨）** | 「最高到達率」を別に保存し、下がったときは `72%（最高 75%）` と併記 | 数字が2つ出る |
| B | 星が増えた日を境に、率を「その日の星の数」で固定した別系列にする | 実装が重い |
| C | 増えた星は、開いて見るまで分母に入れない | 分母が人によって変わる |

いまも「空が広がっただけです」という説明は出していますが、**数字そのものが下がらない**のは A だけです。

### ③ localStorage は同じオリジンの別アプリからも読めます

`https://moritikuwa.github.io/apps/` には `yoilog` も同居しています。
ブラウザの仕様上、同じオリジンのページからは `seiza.v1` を読めます。
いまは外に出す仕組みがないので実害はありませんが、**外部送信を足すなら、ここは先に潰す前提**です。

## 2. Claudeアカウント直接接続の可否

### 結論：❌ **現時点では実装不可**

「森さんが普段使っている claude.ai のアカウント」に、アプリから直接つなぐ公式な方法は**ありません**。

### 根拠

| 調べたこと | 結果 |
|---|---|
| 公式APIの入口 | `https://api.anthropic.com`。Messages / Batches / Token Counting / Models（正式）、Files / Skills / Agents / Sessions / Environments（ベータ） |
| 認証方式 | `x-api-key`（**Console で発行する APIキー**）、または Workload Identity Federation の `Authorization: Bearer` |
| claude.ai の会話履歴・個人スキル・使用状況を取るAPI | **公式ドキュメントに存在しない** |
| Admin API で個人の情報が取れるか | **取れない**。公式に明記：*「The Admin API is unavailable for individual accounts.」*（個人アカウントでは使えない）。さらに中身は組織のメンバー・ワークスペース・APIキー管理であって、会話や個人スキルは対象外 |
| Cookie / セッショントークンの流用 | 指示書で禁止。加えて利用規約・安全性の両面から不可 |
| ブラウザから直接 API を叩けるか | **叩けません**。実測で確認（下記） |

### 実測：ブラウザ直叩きは CORS で塞がれています

GitHub Pages のオリジンを名乗って、`api.anthropic.com` にプリフライトを投げた結果：

```
> OPTIONS https://api.anthropic.com/v1/messages
> Origin: https://moritikuwa.github.io

< HTTP/2 400
< vary: Origin
< access-control-allow-headers: x-api-key,anthropic-version,content-type

Disallowed CORS origin
```

**許可されていないオリジン**として弾かれます。
そもそもブラウザから叩けたとしても、APIキーを画面側に置くことになるので、指示書の
「認証トークン、APIキー、秘密情報をブラウザ側へ保存しないでください」に真正面から反します。

### ⚠️ 条件付きでできること（別物なので注意）

**Console の APIキーを、サーバー側にだけ置く**なら、Messages API や Skills API は使えます。
ただしこれは「森さんの claude.ai アカウントに繋ぐ」ことではありません。

| | claude.ai（Pro / Max） | Claude API（Console） |
|---|---|---|
| 何 | 普段チャットしている場所 | 開発用のAPI |
| 請求 | 月額 | **使った分だけの従量課金（別請求）** |
| 会話・個人スキルを外から読めるか | **不可** | そもそも別物なので対象外 |
| アプリから使えるか | 不可 | サーバー経由なら可 |

**同じ「Claude」でも、財布も中身も別**です。ここを混ぜると「繋がったのに何も取れない」ことになるので、明記しておきます。

### では「私のAI環境」はどうやって見るのか

前回やった評価（スキルファイル43個を読んで採点した件）は、**Claude Code が森さんのPC／このセッションでファイルを読んだ**からできました。
つまり、AI星座から見るなら道は次章の「ローカル連携」です。**アカウント接続ではなく、手元のファイル経由**が唯一の正攻法です。

## 3. 推奨アーキテクチャ

### 考え方

指示書の3層（フロント／バックエンド／収集）は、最終形としては正しいです。
ただし**最初からそこへ行くのは損**だと考えます。理由は3つ。

1. いまのアプリは**依存ゼロ・サーバーゼロ**で、これが壊れにくさの本体になっている
2. やりたいこと（自動収集して、持ち技と照合して、承認して技にする）は、**GitHub Actions だけで、サーバーを立てずに実現できる**
3. サーバーを立てた瞬間、月額・鍵の管理・落ちたときの対応が全部こちらに乗る

### 推奨：段階を分ける

```
Phase 1  ブラウザだけ（サーバーなし・鍵なし）
  AI星座 ──読み取り専用──▶ api.github.com（公開データ・認証不要）
  AI星座 ◀──手で貼る／読み込む── 診断JSON

Phase 2  収集はGitHubの中で回す（サーバーなし）
  GitHub Actions（毎朝）──▶ 収集 ──▶ 持ち技と照合 ──▶ 候補を Pull Request
  森さんが GitHub で中身を見て、マージした分だけ星になる
  AI星座 ──読み取り専用──▶ 公開された候補ファイル

Phase 3  手元の実績を取り込む（サーバーなし）
  Claude Code の Hooks ──▶ ローカルに集計ファイル ──▶ 手動で読み込み

Phase 4  ここで初めてサーバー（必要になったら）
  AI星座 ──▶ 最小のプロキシ ──▶ Claude API（鍵はサーバーにだけ置く）
```

### なぜこの順番か

Phase 2 の形は、指示書の要求を**構造で満たします**。

| 指示書の要求 | Phase 2 での満たし方 |
|---|---|
| ユーザーの確認なしに書き換えない | Pull Request にするので、**マージしない限り1文字も変わらない** |
| 既定ブランチへ直接書き込まない | Actions は必ず新しいブランチへ |
| 変更前に必ず差分を表示する | GitHub の差分画面がそのまま使える |
| 操作履歴を残す | commit 履歴と Actions のログがそのまま履歴 |
| 最初は読み取り専用 | ブラウザ側は最後まで読み取り専用のまま |
| 秘密情報をフロントエンドへ置かない | ブラウザに鍵を1つも置かない |

**仕組みを追加するのではなく、GitHub が最初から持っているものを使う。** これが一番壊れません。

## 4. 必要なバックエンド候補

Phase 1〜3 では**バックエンドは要りません**。Phase 4 で必要になったときの候補です。

| 候補 | 無料枠 | 秘密の置き場 | 向き | 評価 |
|---|---|---|---|---|
| **GitHub Actions** | 公開リポは無料 | リポジトリの Secrets | 定期実行・PR作成 | ⭐ **収集はこれが最適**。常駐サーバーが要らない |
| **Cloudflare Workers** | 1日10万リクエスト | 環境変数 | APIの中継 | ⭐ Phase 4 の第一候補。CORS を素直に絞れる |
| Vercel Functions | あり | 環境変数 | 同上 | 可。Cloudflare とほぼ同等 |
| Supabase Edge Functions | あり | 環境変数 | DBも要るなら | いまはDBが要らないので過剰 |
| 自前VPS | なし | サーバー内 | 何でも | 月額と保守が乗る。**不採用** |

**推奨：収集 = GitHub Actions、Phase 4 の中継 = Cloudflare Workers。**
中継の役目は「鍵を持って Claude API に代わりに聞き、結果だけ返す」だけに限定します。データは持たせません。

## 5. GitHub認証方式

| 方式 | 判定 | 権限 | ブラウザに鍵を置くか | 使いどころ |
|---|---|---|---|---|
| **認証なし（公開データの読み取り）** | ✅ | 読み取りのみ | 置かない | **Phase 1 はこれで足りる** |
| **GitHub Actions の `GITHUB_TOKEN`** | ✅ | ワークフローに与えた分だけ | 置かない | **Phase 2 の書き込みはここに寄せる** |
| GitHub App（サーバー側で秘密鍵→インストールトークン） | ⚠️ | 最小 `contents:read`、書くときだけ `contents:write` `pull_requests:write` | 置かない（サーバー側） | Phase 4 以降。バックエンド必須 |
| Fine-grained PAT をブラウザに保存 | ❌ | — | **置くことになる** | **不採用**。指示書の禁止事項に反する |
| OAuth Device Flow | 🔎 | — | 置かない設計が必須＝結局サーバーが要る | 下記の理由で断定できず |

### 実測：公開リポの読み取りは、鍵なしでブラウザから直接できます

```
> GET https://api.github.com/rate_limit
> Origin: https://moritikuwa.github.io

< HTTP/1.1 200 OK
< Access-Control-Allow-Origin: *
```

`Access-Control-Allow-Origin: *` が返るので、**ブラウザから直接読めます**。
`moritikuwa/apps` は公開（API で確認済み）なので、`skills.js` や候補ファイルの読み取りに認証は不要です。

- 制限：未認証は **1時間あたり60リクエスト（IP単位）**。1日1回の同期なら問題になりません。

### 🔎 確認できなかったこと

- `https://github.com/login/device/code`（Device Flow の入口）へは、この作業環境から **403** で到達できませんでした。
- `https://docs.github.com` にも到達できません（応答なし）。

Device Flow の細かい仕様（対応スコープ、トークンの寿命、CORSの可否）を**公式ドキュメントで裏取りできていない**ので、推測で書きません。
必要になった時点で、通る環境から確認します。**ただし Phase 1〜2 では Device Flow は使いません**ので、当面ここは止まりません。

## 6. ローカル連携方式

| 方式 | 判定 | 中身 | 評価 |
|---|---|---|---|
| **診断JSONの手動やりとり** | ✅ | いまの「書き出し／読み込み」がそのまま使える | **まずこれ**。追加実装ほぼゼロ |
| **Claude Code の Hooks** | ✅ | 公式機能。`.claude/settings.json` に書く。イベントは `SessionEnd` `Stop` `PostToolUse` など多数。標準入力に JSON が渡る | Phase 3。**送る中身を絞るのが前提**（下記） |
| ローカル常駐ツール（CLI） | ⚠️ | 作れるが、動かし続ける手間と保守が乗る | Phase 4 以降。急がない |
| File System Access API でブラウザから直接読む | ⚠️ | Chromium系のみ。**iOS Safari では動かない** | 森さんはスマホ中心なので**不採用** |

### Hooks で送ってよいもの・送らないもの

指示書に「プロンプト全文、ファイル全文、秘密情報は原則送らないでください」とあります。Hooks は
`transcript_path`（会話ログの場所）や `tool_input`（コマンドの中身）まで受け取れてしまうので、**そのまま使うと確実に踏みます**。

| 送ってよい | 送らない |
|---|---|
| その日に Claude Code を使ったか（はい／いいえ） | 会話の中身 |
| セッション数、ツール実行の回数 | プロンプト全文 |
| 使ったツールの種類（Bash / Edit など）の集計 | ファイルの中身、パス |
| スキルファイルの**個数**と**名前** | スキルの中身 |

つまり Hooks は「**数を数えるだけ**」に使います。これなら火（連続日数）の自動化には十分です。

## 7. データモデル案

### 原則：`seiza.v1` は触りません

既存データを壊さないため、接続まわりは**別のキー**に分けます。片方を消してももう片方は生き残ります。

```
seiza.v1        いまのまま（states / log / runs / streak / daily / badges / seen / ui）
seiza.link.v1   接続に関するものだけ（新設）
```

### `seiza.link.v1` の案

```js
{
  v: 1,

  consent: {                     // 何を外に出すか。同意していなければ通信しない
    accepted: false,
    at: '',
    sends: []                    // 実際に送る項目名の一覧。画面にそのまま出す
  },

  sources: {
    github: { owner:'moritikuwa', repo:'apps', branch:'main', lastSync:'' }
  },

  candidates: [                  // 収集で見つかった、まだ星になっていない候補
    { id:'c001', title:'', url:'', from:'youtube|x|note',
      foundAt:'2026-08-13',
      match:'now|early|before',  // ⚡今すぐ効く / 🔒まだ早い / ⚠先にこれ
      relatedTo:['m3'],          // 持ち技のどれと関係するか
      state:'new|kept|dropped' }
  ],

  local: { lastImportAt:'', sessions:0, runsImported:0 },   // Hooks からの集計だけ

  best: { percent:0, at:'' }     // 第0章②「進捗率を下げない」ための最高到達点
}
```

### 決めておくこと

- **候補は星ではありません。** `candidates` に入っただけでは魔法陣に出ません。森さんが「取る」と決めたものだけが `skills.js` に入って星になります。
- `runs` の本文（`did` / `saw` / `fix`）は**この構造に一切入れません**。外に出す経路を作らないためです。

## 8. セキュリティ上の懸念

### 指示書12章への回答

| 指示書の項目 | いまの状態 | 計画での担保 |
|---|---|---|
| 最小権限で接続する | 接続なし | Phase 1 は認証なしの読み取りのみ |
| 最初は読み取り専用にする | — | ブラウザ側は Phase 4 まで読み取り専用のまま |
| 書き込み権限は変更適用時のみ要求 | — | 書き込みは Actions 側だけ。ブラウザには一切持たせない |
| 秘密情報をフロントエンドへ置かない | 置いていない | **Phase 1〜3 は鍵そのものが登場しません** |
| `.env` や秘密鍵を読み取らない | 読んでいない | Hooks で読むのは件数のみ。ファイル本文は対象外 |
| ログへファイル全文を保存しない | — | `local` は数値だけ |
| 送信前に秘密情報をマスキング | — | そもそも本文を送らない設計にする |
| 変更前に必ず差分を表示 | — | Pull Request の差分画面 |
| 変更は原則として新規ブランチへ | 守っている | Actions は必ず新ブランチ |
| 操作履歴を残す | — | commit 履歴 ＋ Actions ログ |
| 接続解除と保存データ削除 | — | 設定画面に「接続を切る」。`seiza.link.v1` を消すだけで完全に元へ戻る |
| 外部送信する項目をユーザーへ明示 | — | `consent.sends` を画面にそのまま並べる。**空なら何も送らない** |

### このアプリ固有の懸念（4件）

**① 外から集めた文章を `innerHTML` に流すと危険**
`app.js` に9か所、`map.js` に4か所あります。いまは自分で書いた文字しか通らないので問題ありません。
候補（YouTube のタイトルや説明文）を出すときは、**必ず `textContent` を使う**というルールを決めます。ここが今回一番危ないところです。

**② 同じオリジンの別アプリから localStorage が読める**
`/apps/` には `yoilog` も同居しています。外部送信を足すなら、繋ぐのは `seiza.link.v1` だけに限り、`seiza.v1` の本文は経路に載せません。

**③ 候補データそのものが信用できない入力**
外から集めてきた文章は、書いた人が自由に書けます。
それを Claude に「これをやれ」と渡すと、指示の乗っ取り（プロンプトインジェクション）が起こりえます。
候補は**必ず人が読んで承認する**（＝ PR をマージする）形にしておくのは、そのための防波堤でもあります。

**④ 依存ゼロを維持する**
いまライブラリが1つも入っていないことは、それ自体が防御です。
Phase 1〜3 でも npm パッケージは足さない方針にします。
